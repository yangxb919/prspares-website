## 08:45-09:00｜配置｜VPS nginx：xyz 域名 301 + 清理配置冲突 + robots.txt 缓存头

**操作类型**：配置（VPS nginx，非应用代码，不走部署流程）

**涉及文件**：
- VPS `/etc/nginx/sites-enabled/prspares-site`（改）
- VPS `/etc/nginx/sites-enabled/prspares-site.bak.20260512`（移出）
- 备份 `/etc/nginx/backup-20260801/`（orig / step1 / final 三份）
- 新增仓库副本 `ops/nginx/prspares-site.conf` + `ops/nginx/README.md`

### 一、起因
07-31 的 GSC 盘点 + AI 分析中查实：`prspares.xyz` 对 Googlebot **返回 200 而非 301**，
全站内容与主域完全重复，只靠 canonical 指主域。canonical 只决定「算谁的分」，
**无法阻止抓取动作本身** → 抓取预算被两个域名瓜分。而该站 Googlebot 近两周仅 1218 次，
是 AI 爬虫（6943 次）的 1/6，预算本就极紧张。

### 二、三项改动

1. **xyz 内容页 301 → 主域对应路径**（保留 `$request_uri`）
   - 相比 robots.txt 屏蔽的优势：能把 xyz 作为**最早使用的域名**可能积累的历史外链权重传给主域
   - 已确认 Google Ads 落地页全部用主域（`/lp/google-ads-factory-direct.html`），xyz 不参与投放
   - `/healthz` 保留在 xyz 本域直接返回 200，避免监控探针跟随 301 后误判

2. **🔴 `/api/` 排除在 301 之外**（加固）
   前端表单走**相对路径** POST `/api/send-rfq-email`。若 API 也 301，浏览器会把 POST
   降级成 GET 并**丢弃 body** —— 在 301 生效前就已打开 xyz 页面的用户点提交会直接丢询盘。
   xyz 历史上承接过 12/88 的询盘，这条不能省。

3. **清理 sites-enabled 里的 .bak 文件**
   `nginx.conf` 用 `include /etc/nginx/sites-enabled/*`（通配符不限扩展名），
   `prspares-site.bak.20260512` 被当成真配置加载 → 每个 server_name 定义两遍 →
   `nginx -t` 报 **8 条 conflicting server name 警告**。功能未坏（nginx 忽略重复定义），
   但改配置可能改了不生效。已移至 `/etc/nginx/backup-20260801/`。

4. **robots.txt 缓存头 max-age=0 → 86400**
   上游 Next.js 返回 `Cache-Control: public, max-age=0`，导致 Googlebot 两周内重复抓
   robots.txt **303 次 = 其全部抓取预算的 25%**。nginx 层覆盖，
   必须先 `proxy_hide_header Cache-Control` 再 `add_header`，否则两个头同时下发。

### 三、执行方式
带自动回滚的原子操作：先备份到 **sites-enabled 之外**，写新配置到 `/tmp`，
`nginx -t` 通过才 `systemctl reload`，失败自动恢复备份。两轮改动各备份一次。

### 四、验证（全部通过）
| 检查项 | 结果 |
|---|---|
| 主域内容页（/、/wholesale-inquiry、/products/screens） | 200 ✅ |
| xyz 内容页（/、/blog/*） | 301 → 主域对应路径 ✅ |
| xyz `/api/products` | 200 直通 ✅ |
| 主域 `/api/products` | 200 ✅ |
| 两个域名 `/healthz` | 200 ✅ |
| robots.txt | `public, max-age=86400`，**仅 1 个 Cache-Control 头** ✅ |
| `nginx -t` | 干净通过，**8 条 conflicting 警告全部消失** ✅ |

### 五、预期收益（08-07 复查）
- Googlebot 不再重复抓 xyz 的 143 篇文章 → 抓取预算全部回到主域
- 省下 robots.txt 那 25% 的重复抓取

## 09:05-09:15｜配置｜nginx 日志格式加 $host 与 $request_time

**操作类型**：配置（VPS `/etc/nginx/nginx.conf`）

**涉及文件**：VPS `nginx.conf`（改）、备份 `/etc/nginx/backup-20260801/nginx.conf.orig`、
仓库 `ops/nginx/nginx.conf.logging-excerpt.txt`（新）、`ops/nginx/README.md`（补章节）

### 起因
两个域名共用一份 access.log 且 `log_format` 用的是默认 combined（无 `$host`），
导致 07-31 统计的「Googlebot 近两周 1218 次」实际是 **xyz + 主域合计**，主域真实值更低。
另外此前想验证「1GB VPS 是否是 Googlebot 抓取瓶颈」，也因日志无响应时间字段无法证实。

### 改动
定义 `main_host` 格式，在 combined 基础上**行尾追加** `host=$host rt=$request_time`：

```
log_format main_host '$remote_addr - $remote_user [$time_local] "$request" '
                     '$status $body_bytes_sent "$http_referer" '
                     '"$http_user_agent" host=$host rt=$request_time';
access_log /var/log/nginx/access.log main_host;
```

🔴 **新字段必须追加在行尾**：前 8 个字段与 combined 完全一致，`awk '{print $7}'` 取 URL、
`$9` 取状态码的既有分析脚本与**全部历史日志**继续可用。插在开头会让字段全部位移，之前写的
爬虫分析命令全部作废。

### 验证
打三条探测流量后读日志，格式正确：
```
"GET /healthz HTTP/1.1" 200 2 "-" "probe-main"     host=www.phonerepairspares.com rt=0.000
"GET /healthz HTTP/1.1" 200 2 "-" "probe-xyz"      host=prspares.xyz rt=0.000
"GET / HTTP/1.1" 301 178 "-" "probe-xyz-301"       host=prspares.xyz rt=0.000
```
`grep -oE 'host=[^ ]+' | sort | uniq -c` 能正确区分两个域名。

### 顺带观察
日志里捕捉到**真人访客**（Chrome 144 / Edge 144）正从 `prspares.xyz` 浏览博客与询盘页
（referer 为 xyz）——该域名有活跃真实流量，不只是历史残留。301 后这些访客会自动落到主域，
体验连续，询盘功能不受影响（且 `/api/` 已排除在 301 之外）。

### 已知限制
08-01 之前的历史日志没有 `host=` / `rt=` 字段，按 host 过滤会返回空 —— 这是预期行为。
若要对比 08-07 的抓取量，主域基线只能从 08-01 起算。

- ⚠️ 「停止」≠「放弃 Google」：保留全部技术 hygiene，停的是为 Google 扩写新文章

### 二、每日定时任务
链路：`launchd(10:00)` → `~/.local/bin/prspares-cohort-daily.sh`（跳板，一行 exec）
→ `Analytics/scripts/cohort_daily.sh` → `crawl_cohort.py --compare`

**🔴 为什么要多一层跳板**：launchd 直接执行 `~/Desktop` 下的脚本被 macOS TCC 拒绝
（`Operation not permitted`），但**从非受保护目录启动的进程可以正常读写 Desktop 下的文件**。
把入口放 `~/.local/bin/`、逻辑留在项目里，既绕开 TCC 又不必给 `/bin/bash` 授予完全磁盘访问。
跳板里只保留一行 `exec`，不复制逻辑，避免两份脚本不同步。

**为什么用 launchd 而非 cron**：机器睡眠/关机错过时间点后 launchd 会在下次唤醒补跑一次，
cron 直接跳过。断档一天就少一个观测点。

配置副本与运维命令 → `ops/launchd/README.md`。已手动触发验证，launchd 环境下完整跑通 `exit=0`。

### 三、脚本两处加固（都是会导致数据断档的坑）

1. **🔴 非交互凭据加载**：`gsc_fetch.load_credentials()` 在 token 失效时会调
   `flow.run_local_server(open_browser=True)` —— 定时任务里没人点授权，**进程会永久阻塞并占住端口**。
   改为自实现 `load_creds_noninteractive()`：只用缓存 token，能 refresh 就 refresh，
   失效直接抛异常，由调用方降级为「仅日志」快照。（GSC OAuth 处于 Testing 态，token 每 7 天到期。）

2. **同日重跑做字段级合并**：`--no-gsc` 或 token 失效时 GSC 字段为空，原逻辑整体覆盖会把
   当天已采到的 coverage / lastCrawl / 曝光**抹掉**，等于丢一个观测点。改为逐字段合并，
   新值为空则保留旧值。已测：`--no-gsc` 重跑后 20/20 行的 coverage 仍在。
