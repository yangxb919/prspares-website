## 追加：修复两个 P0（同分支）

### P0-1 — 仅带 `product` 参数的深链丢失产品名

**问题**：`hasSpecificProductLine = Boolean(cleaned && productUrl)` 把产品名的保留**绑定在 productUrl 上**。而线上大量真实深链根本不带 productUrl，例如
`?product=iPhone+13+Pro+Max+OLED+Screen+Assembly&category=LCD%2FOLED+Screens`（Supabase #29 Basit 的 page_url）。
这类入口的具体产品名被整个丢掉，销售只看到 `product_interest=LCD/OLED Screens`。这是 origin/master 上的既有缺陷，非本次改造引入。

**修复**：抽出纯函数 `resolveDeepLink(productParam, categoryParam, productUrl)`：
- `product` 值若本身是品类别名（`LCD and OLED Screens` / `Small Parts` …）→ 只当品类提示，不产出 Selected product；
- 其余一律视为具体产品线并**保留名称**，`productUrl` 降为可选，仅决定是否渲染 "View product source" 链接与邮件里的 `Product source link` 行。

**证据**：同一组真实 URL 跑新旧两套逻辑 —— 旧逻辑 `DROPPED`，新逻辑 `KEPT`（url 为空字符串）。

### P0-2 — 「API 只要求 name+email」的注释与测试是错的

**问题**：第一阶段写的注释与测试断言「服务端只要求 name + email」。实际：
- `src/app/api/send-rfq-email/route.ts:70` → `if (!name || !email || !message)` 返回 400 `name, email, and message are required`
- `src/lib/rfq-client.ts` `validate()` → 抛 `Message is required`

即 **`/api/send-rfq-email` 要求 name + email + message 三项**；只有 `/api/lp-inquiry` 才是宽松的 name + email。

更关键的是：本页**总是**给 payload 加 `'[Wholesale Inquiry]'` 前缀，所以客户一个字没写也能满足服务端的 `!message` 判断 —— 需求框形同虚设，询盘到手仍然无从报价。

**修复**：
- `validate()` 增加 `if (!formData.message.trim())` 校验**客户自己填写的字段**（不是拼装后的 `msgParts`），错误文案 `Please tell us what you need so we can quote`；textarea 加必填星号、错误态描边与错误提示。
- 契约检查器改为双向校验：`CLIENT_GATE_STRICTER`（多拦）+ 新增 `CLIENT_GATE_LOOSER`（少拦）+ 新增 `MESSAGE_GATE_NOT_BUYER_TEXT`（拦的不是客户字段）。
- 页面顶部说明文案由「Only your name and email are required」改为「Name, email and what you need」。

### 新增测试（49 → 67）

- **P0-1 真实入口 fixture**：6 条来自 Supabase `page_url` 的真实 URL（product-only 带/不带 category、product+productUrl、两条品类别名、无参数），逐条断言 category / 产品名 / 产品 url。
  这些测试**直接提取并执行 page.tsx 里的 `resolveDeepLink` 本体**（`loadResolveDeepLink()`，剥离一组明确列举的类型标注后 `new Function`），不是镜像实现；标注剥离若遗漏会直接抛 SyntaxError，另有 fixture 专门反证这一点。
- **P0-1 补充**：缺 productUrl 不得抑制产品名；source 链接仍必须以非空 url 为条件。
- **P0-2**：客户端 gate 必须恰好等于 `['email','message','name']`；服务端契约本身仍成立（反查 route + rfq-client 源码）；空 message 被拦；gate 读的是 `formData.message` 而非 `msgParts`；错误文案可操作。
- **反证 fixture**：删掉 message gate → 同时触发 `CLIENT_GATE_LOOSER` + `MESSAGE_GATE_NOT_BUYER_TEXT`；改成校验 `msgParts` → 触发 `MESSAGE_GATE_NOT_BUYER_TEXT`。

**顺带修正检查器自身缺陷**：原 payload 键检测只认 `key:` 写法，ES6 简写（`{ name, email }`）会被误判为「字段丢失」。收紧 fixture 断言（`includes` → `deepEqual`）后暴露出来 —— 说明原先那条 `PAYLOAD_KEY` fixture 是**因为错误原因通过的**。已抽出 `payloadSendsKey()` 同时接受两种写法。
