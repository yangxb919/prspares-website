## 18:20 🔴 事故发现 — Supabase 停服导致全站 137 篇博客 404

- 现象：`/blog` 列表页显示 "No repair guides found"，所有 `/blog/<slug>` 返回 404。

- 时间线（nginx 日志逐日计数）：08-09 尚有 816 次 200 / 71 次 404 → **08-10 起 0 次 200，
  每日 1,000-1,500 次 404**，持续 7 天，累计约 7,800 次。
- 未受影响：首页、`/products/*`（数据来自 `src/data/` 静态目录）、`/wholesale-inquiry`。
- 询盘未丢：`/api/send-rfq-email` 是「Supabase 写入 + 邮件」双通道独立设计，
  只要邮件成功就返回 200。日志显示 08-13 ×3、08-15 ×1 均为 200，询盘应已通过邮件送达（未入库）。

## 18:40 修复 — egress 根因 + 停止把故障当 404

涉及文件：
- `src/app/blog/page.tsx`
- `src/app/blog/category/[slug]/page.tsx`
- `src/app/blog/[slug]/page.tsx`
- `src/components/features/ArticleCard.tsx`

变更说明：
1. **egress 根因**：`/blog` 读取 `searchParams` → Next.js 强制动态渲染 →
   `export const revalidate = 3600` 失效 → **每次请求都真打数据库**，
   而 select 里带了 `content`，等于每次拉 142 篇全文（实测均 17.1 KB/篇 ≈ 2.89 MB/次）。
   按 ~300 次/天算 ≈ 21 GB/月，而 Supabase 免费额度为 5 GB/月。
   → 列表页与 5 个分类页的 select 均移除 `content`，降幅约 84%（→ 0.46 MB/次）。
2. **索引保护**：`blog/[slug]/page.tsx` 末尾 catch 块原先把任何异常（含 Supabase 402）
   都吞成 `notFound()` → 404。改为放行 `notFound()/redirect()` 的导航信号（digest 判定），
   其余一律上抛成 5xx。Google 对 404 会移除索引，对 5xx 才按「临时不可用」保留。
   env 缺失分支同样从 `notFound()` 改为抛错。
3. **软 404**：列表页查询出错时不再渲染 "No repair guides found" 的 200 空页，改为抛错。
4. 配套：`readTime` 改从 `meta.word_count / meta.structured_data.wordCount` 取，
   取不到则不显示（ArticleCard 条件渲染），不编造阅读时长。

验证：`npx tsc --noEmit` 通过。**未 commit / 未 push**（push 会触发自动部署，等用户决定）。

遗留：修复后仍约 4 GB/月，贴近 5 GB 额度。彻底解法是只 select `meta->>category` 等子键
（可降至 ~0.75 GB/月），但项目无该语法先例且 Supabase 停服无法验证，未实施。
