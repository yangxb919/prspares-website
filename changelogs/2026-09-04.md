## 三、🔴🔴 核心发现：全站零静态渲染（架构级根因）

### 现象
- 线上所有页面（含纯静态的 `/products/screens-grade-guide`）返回
  `cache-control: private, no-cache, no-store, max-age=0`
- HTML 响应 **3.4~3.9 秒**，连续两次请求无缓存命中
- 构建产物 `.next/prerender-manifest.json`：**静态预渲染 0 条 / ISR 0 条**（全站 57 路由）

### 根因
`src/app/layout.tsx` 第 81、89 行在**根布局**里调用了 `headers()`：
- 81 行读 `x-pathname` → 判断 `/id/` `/th/` 前缀 → 决定 `<html lang>` 和是否显示 Header/Footer
- 89 行读 `host` → 判断是否 localhost → 决定是否加载 GTM

根布局包裹全站每一个页面，`headers()` 使整棵渲染树 opt-in 动态渲染，于是：
`generateStaticParams()` 失效、`revalidate = 3600` 失效、每个请求都实时渲染并真打 Supabase。

**为了 2 个页面（`/id/wholesale`、`/th/wholesale`，全站共 43 个 page.tsx）的特殊处理，
牺牲了其余 41 个页面的静态渲染能力。**

### 实证（本次做了对照实验，已恢复原状）
临时注释掉那两处 `headers()` 后 `npx next build`：
```
Generating static pages (0/224) → (56/224) → (112/224)
```
**从 0 个静态页变成 224 个**。判断坐实。实验后 `layout.tsx` 已还原，
`git diff` 确认与 HEAD 完全一致，无残留。

### 影响链
```
根 layout 调 headers()
  → 全站动态渲染（静态生成 + ISR 全失效）
  → 每请求真打 Supabase，响应 3.4-3.9s
     ├─ Google 按响应速度降抓取率 → 真 Googlebot 仅 ~87 次/天 → 66 页从没被抓 → 不被索引
     ├─ Supabase egress 暴涨 → 08-10 全站 404 事故的燃料
     └─ 真人首字节 3.4s
```

### 修复方案（✅ 本次已执行，见下方第四节之三）
1. 根 layout 去掉两处 `headers()`
2. `/id/wholesale`、`/th/wholesale` 的 lang + 隐藏 Header/Footer 改用 **Route Groups**
   （多根布局），或接受这两页 lang=en（其 hreflang 已在各自 layout 的 metadata 里正确声明）
3. GTM 的 localhost 判断改用 `NODE_ENV` + 构建期 env，不需要运行时 headers
4. 🔴 连带必修：`/thank-you` 的 `useSearchParams()` 未包 Suspense —— 静态化后才暴露，
   本次实验中它是 2 个 prerender 失败之一（另一个是本地网络到 Supabase 的偶发 fetch failed，非代码问题）

## 四、本次已修（低风险，已改代码）

### 1. `/blog/*` 不存在的 slug 返回 500 而非 404 —— 全站级 bug
**操作类型**：修复｜**文件**：`src/app/blog/[slug]/page.tsx`

`.eq('slug',…).single()` 在查到 0 行时，PostgREST 返回的是 **error（PGRST116）而非空数据**，
而代码是 `if (error) throw error` → 任何不存在的 slug 都 500，下面那句 `if (!postData) notFound()`
是永远执行不到的死代码。实测 `/blog/任意乱码` 稳定 500。

这是 08-10 事故修复时引入的回归：当时为了"别把数据库故障当 404"，把所有 error 都改成 throw，
但没区分「文章确实不存在」和「基础设施故障」。

修法：`error.code === 'PGRST116'` → `notFound()`（真 404）；其余 error 保持 throw（→5xx 保索引）。
`tsc --noEmit` 通过。catch 块原本就已正确放行 `NEXT_NOT_FOUND` digest，无需改。

### 2. 补 3 条缺 `/blog` 前缀的 301
**操作类型**：修改｜**文件**：`next.config.js`

GSC「未找到 404」16 条里，逐条 curl 复核后确认这 3 条是真 404 且目标页线上 200：
`/iphone-charging-port-replacement-guide`、`/phone-screen-repair-pricing-strategy`、
`/wholesale-phone-parts-supplier-uk` → 各自加 `/blog` 前缀。
（前一批 2 条已在 bafebf4 处理过，这是剩下的。）`node -e require` 语法校验通过。

其余 13 条复核结论：8 条已有 308 重定向只是 Google 没重抓；3 条线上已恢复 200（08-10 事故受害者）；
1 条 500（即上面那个 bug）；`/blog/replacement-parts-repeat-orders-repair-shops` 和
`/products/android-phone-parts-manufacturer-supplier` 是 308 到列表页的弱重定向，

## 五、顺带发现：伪造 Googlebot 的漏洞扫描（无损害）

09-01 nginx 日志里"Googlebot"抓取量 5413 次，是平日 100 倍。核查发现
**5372 次来自 `94.154.46.245` / `94.154.46.248`，不是 Google 的 IP 段**
（真 Googlebot 是 66.249.x.x，当天仅约 35 次）。扫的是 `/.env`、`/.env.production`、
`/wp-config.php`、`/config.json`、`/wrangler.toml`、`/yarn.lock` —— 在找数据库凭据和 API key。

**结论：零泄露**。这两个 IP 的状态码分布 = 5352 个 301 + 28 个 400 + 20 个 404，
**一个 200 都没拿到**；`/.env` 线上实测 404 且 0 字节。它们 09-01 之后已消失，无需紧急处置。
