### 背景
`/thank-you` 页面向买家承诺“会收到一封含询盘详情的确认邮件”，但此前后端只给 PRSPARES 管理员邮箱发通知，买家从未收到任何确认——网站承诺与实际行为不符。本次补齐一封简短的纯文本买家确认邮件。

### 行为与安全语义
- **仅在核心捕获成功后才发**：确认邮件不是第三条捕获通道。只有在 `dbOk || emailOk`（数据库写入或管理员通知至少一条成功）之后才尝试发送。
- **失败不影响已捕获线索**：确认邮件的失败只记录日志，绝不把已安全捕获的 RFQ 变成 HTTP 5xx；用独立字段 `customerAckOk` 上报，绝不与管理员邮件的 `emailOk` 混淆。
- **核心 5xx 语义不变**：仍然只有当 DB 与管理员邮件“双双失败”时才返回 500；管理员邮件行为完全未变（收件人、`[RFQ]` 主题前缀、无整体超时）。
- **正文只回显买家可见内容**：仅回显买家自己的留言、所选 product interest；从不包含 IP、user-agent、attribution、UTM/gclid、内部 source 值、内部渠道标记（`[Wholesale Inquiry]` / `Product source:`）、营销归因（`Heard about us:` / `How did you hear about us:`）或 SMTP/配置信息；不编造价格/MOQ/库存。
- **邮件头注入安全 + 自动化标记**：Subject 为纯 ASCII（原始 SMTP 客户端不做 RFC 2047 编码、不协商 SMTPUTF8）；额外邮件头（`Auto-Submitted: auto-generated`、`X-Auto-Response-Suppress: All`）对键值做注入清洗，降低自动回复回环。
- **有界超时 + 真正拆链**：确认邮件走 `CUSTOMER_ACK_TIMEOUT_MS = 15000ms` 的整体超时；超时会 `socket.destroy()` 真正拆掉底层连接（不是 `Promise.race` 让 SMTP 在后台继续），并在 `finally` 中清理定时器。这 15 秒只是**确认邮件 SMTP 阶段本身**的上界，不是整个请求的上界——DB 写入与管理员通知在此之前已经发生并计入请求总耗时；本仓库未配置任何 route/platform `maxDuration`。

### 测试（无任何网络/真实 SMTP）
- 纯构造器直接被提取执行：内容（确认收到、24 小时、回显留言与 product interest、邀请补充型号与数量）、安全（剥离内部标记与营销归因、单行化 product interest 防头注入、超长截断、纯净无内部字段、Subject 纯 ASCII 且 ≤ 15s 界）。
- 有界超时守卫用假 socket + 短定时器做逻辑测试：超时触发真实 destroy、取消后不触发、非正值为 no-op、无 active socket 时安全。
- 路由层源码级断言：确认邮件位于双失败 5xx 闸之后、由 `dbOk || emailOk` 守卫、try/catch 且不改变状态码、独立 `customerAckOk` 字段、只透传安全字段（LP 路由不透传 `source`/结构化消息/`monthlyVolume`/`heardAbout`）。

## 修正：确认邮件 SMTP 超时上界 5000ms → 15000ms

- **时间**：2026-08-06
- **操作类型**：修复
- **涉及文件**：
  - `src/lib/email/sendRfqEmail.ts`（`CUSTOMER_ACK_TIMEOUT_MS` 常量值）
  - `scripts/rfq-customer-confirmation.test.mjs`（对应断言与上界文案）
  - `changelogs/2026-08-06.md`（本文件，回填上文两处 5000ms/5s 描述为 15000ms/15s）

### 背景
针对 PR #3 的受控本地 SMTP 冒烟测试（真实 Zoho `smtppro.zoho.com:587`，发件 `wendy-lee@phonerepairspares.com`，密码取自 macOS Keychain `zoho-prspares-imap`，收件 `yangxb919@gmail.com`）显示 `sendRfqCustomerAck(...)` 在原 5 秒整体超时下抛出 `SMTP overall timeout`，收件方（含垃圾邮件夹）未收到任何邮件——真实 Zoho 路径下 5 秒不够，合并闸门保持关闭。

### 修正内容
- `CUSTOMER_ACK_TIMEOUT_MS` 由 `5_000` 改为 `15_000`；socket-destroy + `finally` 定时器清理设计不变，整体超时上界的"存在"本身不变，仅数值放宽；管理员邮件路径（无整体超时）未触碰。
- 测试断言同步放宽为 `boundMs > 0 && boundMs <= 15_000`，错误提示文案改为 `<= 15000ms`；仍然明确这只是**买家确认邮件 SMTP 阶段**的上界，不代表整个 HTTP 请求被限制在 15 秒内（DB 写入与管理员通知在此之前完成，且本仓库未配置 route/platform `maxDuration`）。
